# C1 Accounting Write Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the approved backend-only C1 accounting write slice: ordinary cost drafts, financial preparation, immutable evidence, explicit publication, audited correction, and canonical subcontract cash recording.

**Architecture:** Extend the existing `project_cost_items` projection with `draft | published`; reuse canonical details and source links; expose computed publish readiness rather than persisting `prepared`. Keep evidence in a private immutable Storage-backed registry, keep `project_subcontract_payments` as the sole subcontract cash ledger, and enforce every capability in both server services and guarded database RPCs.

**Tech Stack:** Nuxt 4/Nitro H3, TypeScript 5.9, Zod 4, Supabase JS 2.112, Supabase CLI 2.114, PostgreSQL/pgTAP/RLS/Storage, Vitest 4, pnpm 10.

**Spec:** `docs/superpowers/specs/2026-09-22-c1-accounting-write-backend-design.md` at commit `a19de1cce16163fdf2f3b6c9bf1ef1336964e38f`.

## Global Constraints

- Execute sequentially on `feat/c1-accounting-write-backend`; do not create a worktree or parallel feature branch.
- Cloud DEV is the only development database. Never use Local DB or Production.
- Cloud mutation requires a separate implementation authorization. Until then, only repository work and read-only `db:dev:target`, `auth-check`, and `status` are allowed.
- P1–P6 migrations are committed and reviewed locally but are not pushed phase-by-phase. P7 dry-runs, rehearses, and applies all six in order only after all dependent server/shared code is complete and a separate Cloud mutation authorization is active.
- Never edit any of the 50 applied migrations through `20260922024724`; every database change is a new forward migration created with `pnpm exec supabase migration new <exact-name>`.
- The timestamp prefix is generated by the CLI and is not renamed. Every contract test resolves exactly one migration by the binding suffix listed below.
- Preserve `work_status` as business state. Persist only `publication_state = draft | published`; readiness is computed.
- Preserve the eight independent permissions: five writes (`cost.manage`, `cost.prepare`, `cost.publish_import`, `cost.correct`, `cost.record_cash`) and three reads (`cost.read`, `cost.source.read`, `cost.file.read`).
- No authenticated direct business-table DML. Public `SECURITY DEFINER` wrappers recheck `auth.uid()`, company context, exact permission, state, scope, and version; private functions remain revoked.
- No public evidence bucket, Storage upsert, object overwrite, evidence deletion, fake source figure, or service-role client in normal request paths.
- No second payment ledger. Cash corrections are void plus replacement in `project_subcontract_payments`.
- No implementation under `app/pages/**`, `app/components/**`, styles, visual forms, upload widgets, dialogs, drawers, or Accountant screens.
- No browser/UI acceptance belongs to this backend plan. Antigravity receives a non-visual contract handoff after backend acceptance.
- Keep every phase independently reviewable and commit only the files listed by that task.

## Review Focus

1. **Prepare/publish race:** a publish and a financial replacement with the same version must serialize; one succeeds and the other returns `VERSION_CONFLICT`, never a partial or duplicated amount. Covered by Tasks 5 and 9.
2. **Zero versus unprepared:** a draft with no details has `amount: null`; one explicit zero detail is prepared with `amount: "0.0000"` and is publishable. Covered by Tasks 4, 5, and 9.
3. **Failed evidence finalization:** a wrong MIME/size/hash leaves the registry pending and un-linkable; a new intent/path is required rather than overwriting bytes. Covered by Tasks 7 and 8.
4. **Permission revoked before replay:** every receipt replay reauthorizes before returning its stored result. Covered by Tasks 5, 8, 9, 11, and 13.
5. **Concurrent cash replacement:** one voided payment may acquire at most one recorded replacement; competing requests return `IDEMPOTENCY_CONFLICT`, `VERSION_CONFLICT`, or `PAYMENT_ALREADY_VOIDED` without double-counting. Covered by Tasks 12 and 13.
