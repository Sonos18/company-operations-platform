# Taskovia C1 implementation plan — approved baseline

> **Current execution scope:** This plan remains historical design context. Active Phase 3 work follows [C1 P3R Minimal Project Cost Scope](../../implementation/taskovia-c1/p3r-minimal-project-cost-scope.md): Director-facing Project cost management for contractor/business-item value and execution/acceptance status. It does not authorize the financial-accounting domain previously described below.

## Approved C1 baseline

This plan is documentation only. It replaces conflicting C1 assumptions but authorizes no implementation, migration, data correction, or runtime change.

### Correct Project model

VQH owns two independent Projects:

```text
VQH
├── Project: Eo Gió
└── Project: Yong Mei
```

Yong Mei is not a contractor, engagement, child project, or substitute for a Project. A legitimate Yong Mei Party/Contractor may be retained, but Project identity cannot be represented by that party record.

### Financial semantic rules

C1 presents Actual and Confirmed Obligation only where supported by evidence. It must not infer Budget, remaining budget, utilization, Forecast, estimated completion cost, Profit, Profit Margin, or estimated remaining cost.

- Actual recorded revenue, Actual recorded cost, cash received, cash paid, confirmed receivable, and confirmed payable are distinct.
- Unknown is not zero.
- Recorded cost is not Paid; recorded revenue is not cash received.
- Confirmed obligation is not an estimated future obligation.
- Thu minus Chi is not Profit.
- Missing evidence remains Unknown; a cost record does not prove payment.

## C1 architecture

### Offline preparation

```text
Excel Eo Gió ─────┐
                  ├── CodeX business analysis and mapping ──> Taskovia Database
Excel Yong Mei ───┘                                      Company / Project / financial records /
                                                          categories / parties / obligations
```

Excel is temporary offline source material. CodeX maps approved business meaning into existing generalized Taskovia domain structures. Do not introduce a Data Ingestion Layer, runtime Excel parser, upload service, import dashboard, reconciliation subsystem, workbook-cell tables, or workbook-shaped schema.

### Runtime

```text
UI -> API / Backend -> Taskovia Database -> API / Backend -> UI
```

Taskovia Database is the runtime business source of truth. There is no runtime UI -> Excel or API -> Excel dependency. Directors and business users do not open Excel to verify Taskovia figures.

## API and aggregation direction

Use Project-identity reads following existing conventions (conceptually `GET /projects/:projectId/financial-summary`). Aggregate from Taskovia DB by `company_id + project_id`, not workbook identity. Responses expose business concepts: Project, Actual Thu/Chi where known, confirmed obligations where established, category/party breakdowns, and explicit Unknown states. UI must not understand workbook, sheet, cell/range, or reconciliation status.

## Director financial UI

The Project experience is:

```text
Project -> Financial Overview -> Thu | Chi -> financial composition -> business detail
```

Each independent Project has its own overview. The first view prioritizes Actual Thu and Actual Chi; confirmed receivable/payable appear only when evidence exists. Unavailable metrics remain Unknown/no confirmed data, never fabricated zero.

Chi drill-down is Project -> canonical cost category -> party/contractor/business item -> detail. Do not hard-code spreadsheet labels as categories without business validation.

Normal business UI removes `Phạm vi`, Excel `Vị trí`, `Cần đối chiếu Excel`, `Chưa đối chiếu`, sheet/range, and source-file metadata used solely for manual reconciliation. Where appropriate, `Giá trị nguồn` becomes business-facing `Giá trị`.

## Data ownership and isolation

Every persisted record resolves to VQH plus either Project Eo Gió or Project Yong Mei. Runtime cannot infer ownership from workbook names. Duplicated Eo Gió material in a Yong Mei workbook is excluded from Yong Mei until explicit evidence proves ownership. Aggregation must prevent cross-project inclusion and duplicate counting.

## Future implementation phases

1. **Domain and data assessment:** document current Eo Gió/Yong Mei, related financial/party records, conflicts, reusable structures, and a precise non-destructive correction map.
2. **Project boundary correction:** plan safe remapping to two independent VQH Projects while preserving legitimate party entities.
3. **Financial semantic correction:** normalize supported facts as Actual, Confirmed Obligation, and Unknown; remove unsupported Budget/Forecast/Profit assumptions.
4. **Project financial aggregation:** plan DB-backed `company_id + project_id` summaries that prevent cross-project aggregation and double counting.
5. **Director financial UI:** replace source/reconciliation-first UX with Project Thu/Chi overview, composition, and business detail.
6. **Acceptance hardening:** verify isolation, totals, Unknown handling, Actual/Paid distinction, obligation evidence, duplicate prevention, absence of unsupported inference, and no Excel reconciliation dependency.

## Acceptance criteria

1. Eo Gió and Yong Mei are independent Projects with persisted correct ownership.
2. Runtime follows UI -> API -> DB; Excel is outside runtime.
3. Business users do not reconcile Taskovia against Excel.
4. Director Project UI is a financial business overview, not a source audit table.
5. Actual, Paid, Confirmed Obligation, and Unknown remain distinct; Unknown never becomes zero.
6. No Budget, Forecast, Profit, Profit Margin, or estimated remaining cost is inferred without approved data.
7. Aggregation is Project scoped and prevents double counting.
8. Existing generalized domain structures are reused where correct; no Excel-specific schema merely mirrors workbook layout.
9. Current implementation debt is explicit before future correction.

## Non-goals

- Data Ingestion Layer or automated Excel import pipeline
- User-facing Excel upload or spreadsheet reconciliation workflow
- Budget management, forecasting, profit calculation, or profitability prediction
- Full accounting system
- Unrelated Taskovia redesign

## Risks and unresolved mappings

Do not guess whether Yong Mei remains a legitimate Party, which records belong to each Project, payment/cash status, obligation evidence, or canonical categories. Do not treat source workbook names, copied content, or source figures as proof of Project ownership.

## Retained and deprecated C1 work

Retain compatible authentication, tenant/company isolation, Project/Party structures, decimal handling, provenance, and read-only access controls. Future phases must correct source/reconciliation-first Director UI and any Yong Mei-under-Eo-Gió assumption. This plan does not rewrite history or claim the target is already implemented.
